# 浮点数为什么不准：0.1 + 0.2 ≠ 0.3

## 二进制小数的先天问题
十进制下 $\frac{1}{3} = 0.3333\ldots$ 写不完；二进制下 $0.1$ 同样写不完：
$0.1_{10} = 0.0001100110011\ldots_2$，是无限循环小数。计算机必须在某一位截断，误差从这里出生。

## IEEE 754 双精度的布局
64 位分成三段：1 位符号、11 位指数、52 位尾数。
数值 $= (-1)^s \times 1.f \times 2^{e-1023}$（规格化数）。
52 位尾数意味着大约 15~16 位十进制有效数字；相邻两个可表示数之间的间隔随指数增大——
$10^{20}$ 附近的间隔是 $16384$，加个 1 根本不会被看见。

## 三条经典事故链
1. **舍入累积**：$0.1 + 0.2 = 0.30000000000000004$。逐次运算各自舍入，误差叠加。
   金融系统用整数分记账、或用十进制类型，就是在绕开它。
2. **大数吃小数**：$10^{16} + 1 = 10^{16}$。求和时先加小数再加大国，能显著减小损失。
3. **相等判断**：浮点数永远不要用 `==` 比较。标准做法是 $|a - b| < \varepsilon$，
   且 $\varepsilon$ 应随量级缩放（相对误差），而不是一个写死的全局常数。

## 工程直觉
把浮点数想成"科学计数法的不完美实现"：表达范围巨大（约 $10^{\pm308}$），
代价是有限精度下的不可结合——$(a+b)+c$ 与 $a+(b+c)$ 可以不相等。
写算法时，误差不是 bug，是这门算术的物理属性，需要被设计进去。
